[RAG & Vector Databases](/docs/rag-and-vector-databases) covered giving a
model information it wasn't trained on. This lesson covers the other
structural limit of a deployed [LLM](/docs/llms): on its own, it can only
produce text — it cannot look anything up, run code, query a database, or
send an email. Whatever "actions" it appears to take in an application
are actually the *application* acting on the model's text output, not
the model doing anything itself.

## Tool use: letting the model take (indirect) actions

**Tool use** (also called function calling) addresses the
can't-do-anything limitation. The model is given a description of
available tools — a web search function, a calculator, an internal API —
each with a name, a description, and a schema for its inputs. Instead of
directly answering, the model can output a *structured request* to call a
specific tool with specific arguments; the surrounding application
actually executes that call, and feeds the result back into the model's
context so it can use it to continue answering.

Crucially, the model itself never runs code or hits an API — it only ever
produces text (here, a structured tool call). The actual execution,
authentication, and side effects are entirely the responsibility of the
application wrapped around the model. Tool use just gives the surrounding
system a clean protocol for extending what the model can effectively
accomplish, without changing what the model fundamentally is.

<Deeper title="What a tool schema actually is">

A tool is described to the model as a name, a natural-language
description, and a machine-readable parameter schema — in practice, JSON
Schema:

```json
{
  "name": "get_weather",
  "description": "Current weather for a city.",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string" },
      "unit": { "type": "string", "enum": ["c", "f"] }
    },
    "required": ["city"]
  }
}
```

The model's output for a call is then structured arguments —
`{"city": "Berlin", "unit": "c"}` — not a sentence like *please look up the
weather in Berlin*. The reason is entirely on the application's side: prose
has to be parsed, and parsing free text is ambiguous and brittle, whereas a
schema-conforming object can be validated and passed straight to a function
call.

Mechanically nothing new is happening. The model is still sampling tokens
from $P(x_t \mid x_{<t})$; the schema simply appears in its context, and
fine-tuning has taught it to emit tokens that parse as valid JSON in that
position. Providers additionally enforce this with **constrained decoding**:
at each step the sampler zeroes the probability of any token that cannot
continue a valid parse, renormalising over what remains. That converts
*usually well-formed* into *always well-formed*, but it guarantees only
syntax — never that the chosen tool or the chosen arguments were the right
ones.

</Deeper>

A practical problem tool use created: every application wiring an LLM to
its own tools originally had to define its own bespoke integration.
**MCP (Model Context Protocol)** is an open standard, introduced by
Anthropic in late 2024, that standardizes how applications expose tools
and data to LLMs — letting a tool built once be reused across different
LLM-powered applications, the same way a USB standard means a peripheral
doesn't need custom wiring for every computer it plugs into.

## Agents: chaining tool use over multiple steps

An **agent** is what you get when you put an LLM in a loop with tool use
and let it decide, autonomously, which tools to call and in what order to
accomplish a goal — rather than a single request/response with at most
one tool call:

<Mermaid chart={`flowchart TD
  G[User goal] --> C[Model reads<br/>the context]
  C --> D{Needs a tool}
  D -- No --> F[Final answer]
  D -- Yes --> T[App executes<br/>the tool call]
  T --> R[Result appended<br/>to the context]
  R --> C
`} />

<Steps>
<Step>
Given a goal and the current context, the model decides: respond
directly, or call a tool.
</Step>
<Step>
If it calls a tool, the application executes it and appends the result
to the context.
</Step>
<Step>
Repeat from step 1, until the model decides the goal is achieved and
produces a final response.
</Step>
</Steps>

This is a genuinely different mode from a single Q&A exchange: an agent
might search the web, read a file, run a calculation, and check its own
intermediate result against the original goal — several LLM calls chained
together, each one building on tool results from the previous step, all
directed at one overall task rather than one prompt.

The tradeoffs are real: more steps means more opportunities for the model
to make a wrong call, and errors can compound across a chain rather than
being isolated to one response — which is why practical agent systems
usually add guardrails (limits on how many steps to take, confirmation
before high-stakes actions, structured output validation at each step)
rather than letting a model loop entirely unsupervised.

<Deeper title="Why long agent chains compound error">

Model a run as $n$ steps, each independently correct with probability $p$,
where a step means one tool choice plus one interpretation of its result.
If the task needs *every* step to be right, the run succeeds with
probability:

$$
P(\text{success}) = p^{\,n}
$$

The exponent is the whole story. At $p = 0.95$, five steps give $0.77$ and
twenty steps give $0.36$ — the per-step reliability barely changed, but the
task went from usually working to usually failing. Equivalently, holding a
target success rate $P$ fixed, the reliability each step must hit is
$p = P^{1/n}$, which climbs steeply in $n$: a 90%-reliable 20-step task
needs $p \approx 0.995$ per step.

The independence assumption is a simplification in both directions. Errors
often *correlate* — a bad early retrieval poisons the context every later
step reads, so failures cluster. But agents can also recover: a step that
checks its own intermediate result turns some wrong steps into retries
rather than failures, which is precisely why verification steps and step
budgets buy so much. The design implication is the same either way — fewer,
more reliable, verifiable steps beat longer autonomous chains.

</Deeper>

<NapkinMath title="The cost of a growing context">

An agent re-sends its **entire** context on every iteration — the original
goal, plus every tool call and result appended so far. Say the prompt starts
at 2,000 tokens and each step adds 1,000 tokens of tool output.

Over 10 steps, the input tokens processed per step are 2k, 3k, 4k … 11k —
about **65,000 tokens total**, not the 12,000 a single final call would
suggest. Run 20 steps and it is roughly **250,000**.

The cost grows with the *square* of the step count, and so does latency,
since prefill work scales with prompt length. This is why agent frameworks
truncate, summarise, or cache context rather than letting the transcript
grow unbounded — and why a step budget is a cost control, not just a safety
rail.

</NapkinMath>

## Combining agents with retrieval

RAG and tool use aren't mutually exclusive — a well-built agent commonly
has *retrieval* (from [RAG & Vector Databases](/docs/rag-and-vector-databases))
as one of its available tools ("search internal docs") alongside other
tools (web search, code execution, sending a message), and decides which
to invoke, and in what sequence, based on the specific request. The
pattern underlying all of it is the same one from the start of this
lesson: the LLM itself stays a frozen, text-in-text-out model; RAG and
tool use are both ways of enriching what goes *into* that model and
acting on what comes *out* of it.

<Misconception claim="a big enough context window makes retrieval unnecessary.">
  Two things stay true no matter how long the window gets. Private and
  current data still has to come from *somewhere* — pasting it in is
  retrieval, just done by hand and without ranking. And attention cost grows
  with sequence length, so every irrelevant token you paste in is paid for in
  latency and money on every single request. Accuracy also degrades in
  practice: models are measurably worse at using information buried in the
  middle of a very long prompt than the same information placed near the
  edges. Retrieval is what decides *which* text is worth the window.
</Misconception>

## Recap and what's next

Tool use gives a model a clean protocol for taking indirect action; MCP
standardizes how those tools are exposed; agents put the model in a loop
so it can chain steps together toward a goal, at the cost of compounding
error and growing context. Together with
[Prompt Engineering](/docs/prompt-engineering) and
[RAG & Vector Databases](/docs/rag-and-vector-databases), this is the
full applied toolkit for turning a single trained model into a real,
capable application — which the final lesson ties together.
